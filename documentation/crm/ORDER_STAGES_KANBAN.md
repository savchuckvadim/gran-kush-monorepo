# Стадии заказов: полоса в карточке и канбан

TASK-673, 2026-10-13. Образец — сделки Битрикс24 (полоса стадий в карточке, канбан по стадиям).

## Как было

- Стадии заказа уже есть: воронка `default` сущности `order` (Pending → Confirmed → Preparing →
  Ready → Completed / Cancelled), клуб правит её в «Настройки → Сущности → Заказ → Стадии».
- Но статус заказа выводился из **названия** стадии (`stage.name.toLowerCase()`), а смена статуса
  искала стадию по названию. Клуб переименовал стадию — статус ломался.
- Названия стадий только английские, без перевода.
- Карточка заказа — кнопки шести захардкоженных статусов, список — бейджи этих статусов.

## Решения

- **Источник правды — стадия.** Новый вызов `PATCH /crm/orders/:id/stage { stageId }` (manager+).
  Поле `status` в ответах остаётся для совместимости и выводится из стадии: `FAILURE` → cancelled,
  `SUCCESS` → completed, старые имена → свой статус, иначе `NEW` → pending, `IN_PROGRESS` → confirmed.
- **Переходы.** Между рабочими стадиями (`NEW`, `IN_PROGRESS`) — в любую сторону, как в Битриксе.
  Закрытый заказ (стадия `SUCCESS` / `FAILURE`) больше не двигается. Отмена возвращает товар на склад.
- **Гонки.** Смена стадии — compare-and-set по текущей стадии записи: две параллельные отмены не
  вернут товар на склад дважды, проигравший запрос получает 409.
- **Перевод названий.** `stages.name_i18n` и `global_stage_templates.name_i18n`; переводы системной
  воронки заказов дописывает стартовый синк (тот же, что для полей и статусов). Переименованная
  клубом стадия показывается его словом на всех языках.
- **Канбан.** Колонки — рабочие стадии выбранной воронки: шапка-шеврон цвета стадии, число и сумма
  заказов, у карточки полоса цвета стадии, колонка прокручивается сама и догружает по 20.
  Закрывающие стадии («Завершён», «Отменён») — зоны внизу экрана, появляются при перетаскивании.
  Закрытие спрашивает подтверждение. Закрытые заказы — в списке.
- **Полоса стадий в карточке.** Шевроны рабочих стадий: пройденные и текущая закрашены цветом
  текущей, будущие серые. Последний сегмент — «Завершить» с выбором закрывающей стадии.
- **Кто двигает.** manager, admin, владелец. У employee полоса и канбан только для чтения.

## API

| Вызов                                               | Что делает                                                                                                                   |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `PATCH /crm/orders/:id/stage`                       | Перевести заказ в стадию; 400 — стадия не из воронок заказов клуба или заказ закрыт; 409 — стадию сменил параллельный запрос |
| `GET /crm/orders/stages/summary?categoryId=`        | Число и сумма заказов по стадиям воронки; те же фильтры, что у списка                                                        |
| `GET /crm/orders?stageId=`                          | Список заказов стадии (колонка канбана, фильтр списка)                                                                       |
| `GET /crm/settings/entities/order/stage-categories` | Воронки и стадии; названия переведены на язык запроса                                                                        |
| `PATCH /crm/orders/:id/status`                      | Оставлен для совместимости: находит стадию по старому статусу и переводит туда                                               |

## Устройство

### UI-библиотека (`packages/ui`, `@workspace/ui`)

Общие части, ничего не знают о заказах:

- `shared/kanban/` — канбан на `@dnd-kit/core`: `KanbanBoard` (контекст, сенсоры, оверлей, зоны
  сброса), `KanbanColumn` (своя прокрутка), `KanbanColumnHeader` (шеврон цвета стадии с числом),
  `KanbanItem`, `KanbanDropZone`. На нём же теперь канбан смарт-процессов
  (`pages/entity-records/records-kanban.tsx`) — без выпадающего списка в карточке.
- `shared/stage-steps/` — `StageSteps` и `StageStep`: шевроны полосы стадий; цвет текста подбирается
  к заливке (`lib/color.ts`), форма — `lib/chevron.ts`.
- `shared/confirm-dialog/` — `ConfirmDialog`; на нём и подтверждение смены статуса участника.
- `shared/load-more/` — `LoadMoreTrigger`: догрузка, когда кнопка доезжает до видимой области.
- `shared/initials-avatar/` — инициалы ответственного на карточке.
- Тема: токены `success` / `warning` (и `*-text`) в `globals.css`. Раньше их не было, и `text-success`
  на страницах согласия и регистрации по ссылке не красил.

### CRM (`apps/crm/modules`)

- `entities/order/` — API, ключи запросов, хуки (по одному на файл), модель (`order-stage.ts`,
  `order-payment.ts`, `order-cache.ts` — оптимистичный перенос), бейджи и ссылка на участника.
- `entities/portal/hooks/portal-role.hook.ts` — `usePortalRole()`: роль сотрудника в клубе, те же
  списки, что у API (`AdminGuard`, `RequireManager`). Им же пользуются шапка и меню аккаунта.
- `features/order-stage/` — смена стадии: полоса стадий, сегмент «Завершить», подтверждение закрытия,
  хук `useOrderStageMove` (оптимистично, при ошибке откат и тост).
- `widgets/orders/` — карточка заказа из маленьких частей, список, канбан, фильтры, шапка с видом.
- `pages/orders/` — страницы списка и карточки; маршруты в `app/` только рендерят их.
- `shared/lib/` — `useMoneyFormat`, `useDateTimeFormat`, `useCompactDateFormat`, `personName`.
- Вид «Список / Канбан» — в адресе (`?view=kanban`, иначе последний выбор на устройстве), воронка —
  `?funnel=` (переключатель виден, когда воронок больше одной).

### Ловушки

- **Привязка прокрутки доски.** `snap-x` на доске превращал каждый автоскролл dnd-kit в прыжок на
  целую колонку, и карточка падала в соседнюю. Во время перетаскивания доска `snap-none`.
- **`asChild` и `data-slot`.** Radix-триггер (`PopoverTrigger asChild`) передаёт свой `data-slot`;
  у `StageStep` атрибут стоит после проброса пропсов, иначе шеврон «Завершить» терял слот.
- **Ссылки в карточке** — `draggable={false}`: родное перетаскивание ссылки мешает dnd-kit.

## Не входит

- Создание заказа из CRM («+ быстрый заказ» в колонке): заказы создают участники в кабинете.
- Слайдер карточки поверх канбана — TASK-672.
- Способ оплаты: кнопки есть, но API его не сохраняет (поля в схеме нет) — отдельная задача.

## Воронки смарт-процессов и порядок карточек (TASK-685, TASK-686, 2026-10-17)

Канбан смарт-процесса показывал стадии всех воронок вперемешку, а карточки в колонке стояли по
дате создания. Теперь он устроен как канбан заказов: одна воронка, оптимистичный перенос, порядок
карточек, который запоминается.

- **Воронка.** Селект воронок стоит рядом с фильтром и общий для таблицы и канбана (`?funnel=`,
  виден, когда воронок больше одной). Колонки — стадии выбранной воронки. Запись создаётся в первой
  стадии выбранной воронки (`POST …/records` принимает `stageId`; чужая стадия — 400).
- **Порядок карточек.** `EntityRecord.stagePosition` (double, меньше — выше). Умолчание в БД — минус
  время создания в мс: новая запись встаёт наверх своей стадии без запроса, у существующих порядок
  прежний («новые сверху»). Клиент называет только соседа сверху (`afterId`), соседа снизу сервис
  находит сам — порядок верен, даже если на экране загружена часть колонки. Между соседями —
  середина; когда double исчерпал точность, колонка перенумеровывается одним `UPDATE` с тем же порядком.
- **Перенос.** `PATCH /crm/entities/:code/records/:id/stage` и `PATCH /crm/orders/:id/stage` принимают
  `afterId` (`null` — наверх). Без него новая стадия ставит карточку наверх, та же стадия ничего не
  меняет. С `afterId` в той же стадии это перестановка: заказ при этом не проходит compare-and-set и
  не получает меток жизненного цикла. Записи смарт-процессов и заказы делят `StagePositionService`.
- **Список.** `GET …/records` принимает `stageCategoryId` (воронка) и `sortBy=stagePosition` (порядок
  колонки); `GET /crm/orders?sortBy=stagePosition` — то же для заказов. У стадии записи в ответе
  есть `stageCategoryId` и название на языке запроса.
- **Доска.** `KanbanItem` теперь и цель сброса: под курсором верхняя или нижняя половина карточки
  решает, встанет перенесённая до или после неё, место показывает линия. Пустое место колонки —
  «под последнюю». `KanbanBoard.onMove(itemId, targetId, placement)`; соседа для API считает
  `kanbanAfterId(ids, movingId, placement)`, «встала на то же место» — `kanbanStaysPut`. Промежуток
  между карточками принадлежит верхней (`pb-2.5` слота), а не колонке: иначе указатель в щели
  отправлял бы карточку в конец. Над пустотой (шапка колонки, щели между колонками, страница) цели
  нет, и отпускание там ничего не делает — так палец отменяет перенос; без указателя (клавиатура)
  берётся ближайшая цель.
- **CRM.** `entities/entity-records/` — ключи, кэш (`applyOptimisticRecordMove`), колонка с
  догрузкой по 20, оптимистичный перенос с откатом; `pages/entity-records/` — страница, таблица на
  `EntityList`, канбан, форма записи. Общие части заказов и записей: `shared/lib/use-board-view`
  (вид и воронка в адресе), `BoardViewSwitch`, `FunnelSelect`, `KanbanColumnFooter`, `pickFunnel`.

### Ограничения

- Запись смарт-процесса не остаётся без стадии: клуб удаляет стадию — её записи уходят в первую из
  оставшихся стадий воронки, удаляет воронку — в первую стадию воронки по умолчанию (иначе запись
  пропала бы с экрана: список и доска выбирают записи по стадии воронки). Системные сущности
  (заказы) так не двигаются — закрытый заказ нельзя «открыть» удалением стадии, их стадия
  обнуляется, как раньше. Уже осиротевшие записи (стадии удалены до этого изменения) надо один раз
  назначить вручную через API.
- Закрывающие стадии смарт-процесса — обычные колонки: зон сброса и подтверждения закрытия, как у
  заказов, у записей нет.
- `GET /crm/orders?sortBy=stagePosition` всегда сверху вниз (направление `sortOrder` не учитывается),
  как и у записей смарт-процессов.
