### TASK-602: API фильтрации по содержимому `[x]` — `feat/entity-filter`

**Сделано (2026-10-12).** Контракт: `q` + `filter` — JSON-массив `{field, op, value}`, op —
`contains | eq | in | gte | lte` (скобки `filters[x]=` простой парсер query в Express 5 не
разбирает, поэтому строка JSON; прежний `?fields[...]` у записей молча не работал). Сборка
условий — `EntityRecordFilterBuilder` (entity-fields, infrastructure): фильтры Prisma по JSON без
сырого SQL; «содержит» через `path: []` (без него Prisma 7 зовёт `lower(jsonb)` и падает),
`%`/`_` экранируются; поле не того типа, чужое или неизвестное → 400. `q` — каждое слово должно
найтись в текстовом поле, у участников ещё в email и номере. `GET /crm/members` стал постраничным
(`{ items, total, page, limit, totalPages }`), записи сущностей — на том же DTO. `filter-fields`
отдаёт все фильтруемые поля с флагом `showInFilters`. e2e — `test/entity-filter.e2e-spec.ts`
(21 тест). Замер на 10k участников не делали.

- Сейчас в списках только `filterFieldKey` + `filterValue` с точным равенством. Нужен общий
  контракт для всех списков сущностей: `q` (строка, поиск по значениям текстовых полей и системным
  колонкам) + `filters[fieldKey]=value|a..b|v1,v2`.
- Один `@Query()` DTO на хендлер (`IntersectionType(PaginationDto, EntityFilterDto)`), правило из
  CLAUDE.md.
- Для текста — `contains` без учёта регистра по `valueJson` (Postgres `ILIKE` на `valueJson::text`
  или по индексу — замерить на 10k участников); для селектов — `in`; для чисел/дат — диапазон.
- Поиск `q` можно собрать на базе `CrmSearchRepository.searchMembers` (Ctrl K), чтобы логика
  была одна.
- e2e: изоляция портала при поиске по полю (клуб A не видит B), совпадение по подстроке,
  неизвестный `fieldKey` → 400.
