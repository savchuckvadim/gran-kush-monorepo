### TASK-101: уникальный ключ платежа `[x]` (2026-08-28)

- [x] `@@unique([provider, externalId])` на `Payment` + миграция `20260828120000_payment_idempotency_keys`
- [x] Нарушение уникальности не доходит до исключения: вставка идёт через
      `createMany({ skipDuplicates: true })` (`ON CONFLICT DO NOTHING`), затем чтение по ключу —
      `PaymentsService.recordProviderPayment` возвращает существующий платёж
- [x] **Почему не `create` с перехватом `P2002`.** Платёж пишется внутри транзакции обработки
      события. В Postgres любая ошибка переводит транзакцию в aborted, и следующий запрос
      обработчика упал бы на «current transaction is aborted, commands ignored until end of
      transaction block». Проверено на живой БД. `ON CONFLICT DO NOTHING` ошибки не порождает,
      а его `count` — тот же сигнал «уже было», что и в TASK-110
- [x] **Частичный индекс не понадобился.** Оба поля nullable, а Postgres считает `NULL`
      различными: ручные платежи (`provider = NULL`) и платежи провайдера без `external_id`
      индекс не ограничивает. То есть `@@unique` уже ведёт себя как
      `WHERE external_id IS NOT NULL`, но живёт в схеме и переживает `prisma migrate dev` —
      в отличие от сырого SQL-индекса (грабли из TASK-109)
- [x] unit-тесты: `apps/api/src/modules/billing/__tests__/payments.service.spec.ts`

Перевод статуса платежа вперёд по машине состояний в эту задачу **не входит** — он требует
compare-and-set и сверки суммы с заказом, это TASK-103. `recordProviderPayment` только создаёт.

### TASK-102: журнал событий провайдера `[x]` (2026-08-28)

- [x] таблица `payment_events`: `provider`, `eventId`, `type`, сырой `payload` (jsonb),
      `receivedAt`, `processedAt`, `failedAt`, `error`, `attempts`
- [x] `@@unique([provider, eventId])` — первый шаг обработки; конфликт означает повторную доставку
- [x] обработчик и отметка `processedAt` — в одной транзакции (`PaymentEventsService.process`)
- [x] подпись проверяется **до единого обращения к БД**; порт `PaymentWebhookVerifier`
      объединяет проверку подписи и разбор тела намеренно: раздельные методы позволяли бы
      разобрать неподтверждённое тело в обход проверки
- [x] **Fail-closed по провайдеру.** Нет зарегистрированного адаптера — запрос отклоняется.
      Отсутствие настройки это «проверить нечем», а не «проверять не нужно»: обратный выбор
      уже стоил нам девяти открытых эндпоинтов каталога (TASK-023)
- [x] unit-тесты: `apps/api/src/modules/billing/__tests__/payment-events.service.spec.ts`

**Дубль и ретрай различаются, а не сваливаются в один «тихий 200».** Событие пишется в журнал
отдельным коммитом до обработки — иначе при откате транзакции обработки исчезал бы и сырой
payload, ради которого журнал и заводится. Отсюда три исхода конфликта по ключу:

| Состояние строки | Что это | Ответ |
|---|---|---|
| `processedAt` заполнен | повторная доставка обработанного события | тихий `200`, эффекты не применяются повторно |
| `processedAt` пуст | ретрай после падения обработки или гибели процесса | событие обрабатывается |
| строки нет | первая доставка | событие обрабатывается |

Если бы конфликт всегда означал «дубль», событие, упавшее в обработке, потерялось бы навсегда:
провайдер прислал бы его снова, а мы ответили бы `200`, ничего не сделав.

Контроллера вебхука пока нет — маршрут и адаптер подписи появляются вместе с выбранным
провайдером, регистрацией в `PAYMENT_WEBHOOK_VERIFIERS`. До тех пор `ingest` отклоняет любой запрос.

### TASK-109: одна открытая сессия присутствия `[x]` (2026-08-26)

- [x] Гарантия на уровне БД: колонка `active_entity_record_id` (nullable) с `UNIQUE`.
      Держит `entityRecordId`, пока сессия открыта, и `NULL` после закрытия; в Postgres
      `NULL` не конфликтует с `NULL`, поэтому закрытых сессий может быть сколько угодно,
      а открытая — ровно одна
- [x] **Почему не частичный индекс.** Прямое выражение правила —
      `CREATE UNIQUE INDEX ... WHERE exited_at IS NULL`, но Prisma не умеет `WHERE`
      в схеме, а индекс, добавленный сырым SQL, начиная с **7.4.0** (наша версия)
      сносится следующим же `prisma migrate dev`: движок видит его как дрейф и
      генерирует `DROP INDEX` — [prisma/prisma#29220](https://github.com/prisma/prisma/issues/29220),
      открыт, обходного пути нет. Колонка эквивалентна по гарантии и переживает генерацию миграций
- [x] Миграция закрывает уже накопившиеся дубли (оставляет самую свежую открытую сессию
      участника), затем backfill и `UNIQUE`
- [x] `createEntry` идемпотентен: при `P2002` по этому индексу возвращает уже открытую
      сессию вместо второй записи. Конфликты по другим полям пробрасываются как есть
- [x] `closeSession` и `closeMany` снимают маркер; `closeMany` теперь фильтрует по
      `exitedAt: null`, чтобы повторный прогон крона не переписывал время выхода
- [x] unit-тесты: `apps/api/src/modules/portal/crm/presence/__tests__/presence-session.repository.spec.ts`
