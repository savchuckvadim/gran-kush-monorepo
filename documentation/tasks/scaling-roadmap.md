# Идемпотентность и масштабирование: план задач

Дата анализа: 2026-08-21. Ветка: `main`.
Разбор и обоснование — [backend/IDEMPOTENCY_AND_SCALING.md](../backend/IDEMPOTENCY_AND_SCALING.md).

Задачи сгруппированы не по темам, а по **моменту, когда они начнут болеть**. Пока приложение
работает в одном экземпляре и без оплаты, ни одна из них не является аварийной — но P0 нужно
закрыть до подключения платёжного провайдера, а P1 до первой второй реплики.

## P0 — до подключения оплаты

Вебхуки провайдеров приходят минимум один раз и не по порядку. Без этих задач первый же ретрай
провайдера создаст второй платёж.

### TASK-101: уникальный ключ платежа `[ ]`

- [ ] `@@unique([provider, externalId])` на `Payment` + миграция
- [ ] обработка нарушения уникальности: возвращать существующий платёж, а не 500
- [ ] решить, что делать с историческими строками без `externalId` (частичный индекс `WHERE external_id IS NOT NULL`)

### TASK-102: журнал событий провайдера `[ ]`

- [ ] таблица `payment_events`: `provider`, `eventId`, `type`, сырой payload, `processedAt`
- [ ] `@@unique([provider, eventId])` — первый шаг обработки вебхука, конфликт → тихий `200`
- [ ] обработка одного события в одной транзакции
- [ ] проверка подписи запроса до любой логики

### TASK-103: идемпотентность денежных проводок `[ ]`

- [ ] ключ идемпотентности на `FinancialTransaction` (например `sourceType` + `sourceId` с уникальным индексом)
- [ ] переходы статусов оплаты через compare-and-set (`updateMany` + проверка `count`), статус двигается только вперёд
- [ ] сверка суммы и валюты с заказом, а не приём из запроса

### TASK-104: Idempotency-Key на создание заказа и платежа `[ ]`

- [ ] таблица `idempotency_keys`: `key`, `scope`, `requestHash`, `response`, `status`, TTL
- [ ] middleware/интерцептор: повтор с тем же ключом возвращает сохранённый ответ
- [ ] клиентская часть в `@workspace/api-client`: генерация ключа на мутацию
