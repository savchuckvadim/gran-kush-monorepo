# Журнал работ (для агентов и людей)

Короткие датированные записи о том, **что сломалось, почему и чем починили** — прежде всего
о неочевидных ловушках, которые нельзя вывести из кода за пять минут. Формат записи:
симптом → причина → правка (со ссылками на файлы). Новые записи добавляются сверху.

## 2026-08-22 — нумерация заказов протекала между клубами

### 1. Номер заказа выдавал объём соседнего клуба

**Симптом.** Клуб, зарегистрированный вторым, создаёт свой первый в жизни заказ и получает
номер вида `ORD-20260822-0037`. Никаких 37 заказов у него не было.

**Причина.** `OrdersService.generateOrderNumber()` брал следующий номер от максимума, который
возвращал `getLastOrderNumberForDate(date)` — а этот метод фильтровал только по дате, без
`portalId`. Нумерация была сквозной по всей базе: по своим номерам клуб B читал дневной оборот
клуба A. Уникальный индекс `(portal_id, order_number)` при этом в схеме был с самого начала
(`orders_portal_id_order_number_key` в init-миграции) — он просто никогда не срабатывал,
потому что сквозная нумерация конфликтов не создаёт.

**Правка.** Метод заменён на
[`getLastOrderNumberWithPrefix(portalId, prefix)`](./../apps/api/src/modules/portal/crm/orders/infrastructure/repositories/order-prisma.repository.ts):
скоуп по порталу + поиск по префиксу номера вместо окна по `orderedAt`.

**Правило на будущее:** любой «человекочитаемый» бизнес-номер (заказ, счёт, договор) нумеруется
в пределах портала. Сквозная нумерация — это не только косметика, это утечка объёмов арендатора.

### 2. Два параллельных заказа получали один номер

**Симптом.** Под нагрузкой создание заказа изредка падало в 500.

**Причина.** «Прочитал максимум → прибавил единицу → вставил» — классическая гонка. После
правки №1 нумерация стала портальной, и уникальный индекс наконец начал ловить дубли: вместо
двух заказов с одинаковым номером теперь `P2002` и 500 в ответ.

**Правка.** В [`orders.service.ts`](./../apps/api/src/modules/portal/crm/orders/application/services/orders.service.ts)
создание обёрнуто в `createWithGeneratedOrderNumber()`: при `P2002` по `order_number` номер
подбирается заново, до 5 попыток. Транзакция создания (`EntityRecord` + `Order` + позиции)
откатывается целиком, а списание склада идёт **после** неё — поэтому повтор ничего не задваивает.
Порядок «сначала запись, потом побочные эффекты» здесь обязателен, не случаен.

### 3. Дневной счётчик сбрасывался в середине дня

**Симптом.** Не проявился в проде (сервер в UTC), но воспроизводим при любой другой TZ.

**Причина.** Префикс номера считался как `toISOString().slice(0, 10)` — то есть **в UTC**, а окно
поиска последнего номера строилось через `setHours(0,0,0,0)` — то есть **в локальной таймзоне**
сервера. При TZ Испании (UTC+1/+2) эти два «дня» расходятся на пару часов: в окно попадали
заказы вчерашнего префикса, и последовательность прыгала.

**Правка.** Дата теперь живёт только в префиксе номера, а поиск идёт `startsWith(prefix)` — одна
точка правды вместо двух представлений одного дня. Заодно запрос ложится на существующий
уникальный индекс `(portal_id, order_number)`.

## 2026-08-21 — dev-окружение, резолв портала, доступ в CRM

### 1. Redis: контейнер и `.env` разъезжались по порту

**Симптом.** API спамил `ECONNREFUSED` на Redis, при этом контейнер был поднят и здоров.

**Причина.** `infra/compose/docker-compose.dev.yml` берёт порт из `REDIS_PORT`. При запуске
голым `docker compose -f infra/compose/docker-compose.dev.yml up -d` переменная не подхватывается
из `apps/api/.env`, compose берёт дефолт из yml, и порт контейнера расходится с `REDIS_URL`.

**Правка.** Инфру поднимать только через `pnpm docker:dev` / `pnpm docker:dev:down` — там уже
прописан `--env-file apps/api/.env`. `REDIS_URL` и `REDIS_PORT` в `apps/api/.env` править вместе.

### 2. Tailwind не резолвится в dev-режиме

**Симптом.** `next dev` валится с `Can't resolve 'tailwindcss' in <repo>/apps`, следом то же
самое про `tw-animate-css`. При этом `next build` проходит зелёным — и это сбивает с толку.

**Причина.** `@tailwindcss/postcss` резолвит `@import` из
[`packages/ui/src/styles/globals.css`](./../packages/ui/src/styles/globals.css) не от CSS-файла,
а от базы `process.cwd()`. В dev Turbopack подставляет базой `<repo>/apps`, где нет `node_modules`;
дальше поиск уходит в корень репозитория. Сами пакеты установлены только в `packages/ui`,
так что в корне их не находит. В `build` база другая — оттуда всё резолвится.

**Правка.** `tailwindcss` и `tw-animate-css` добавлены в devDependencies **корневого**
`package.json`. Это не «мусор в корне» — без них dev-режим не собирает CSS. Не удалять.
Если в `globals.css` появится новый `@import "пакет"`, его нужно так же положить в корень.

### 3. Страница портала отдавала 404 после регистрации клуба

**Симптом.** Клуб зарегистрирован, портал в БД активен, но `/{locale}/{portal}/crm` — 404.

**Причина.** [`[portal]/layout.tsx`](./../apps/crm/app/%5Blocale%5D/%5Bportal%5D/layout.tsx)
при SSR зовёт `GET /crm/portals/resolve?slug=...` и на любой не-2xx делает `notFound()`.
Запрос упирался в `PortalContextMiddleware`: путь начинается с `/crm/`, значит контекст портала
обязателен, а в списке исключений эндпоинта не было → `400 Missing portal`. Замкнутый круг:
эндпоинт нужен, чтобы узнать портал, но от него требовали уже знать портал.

**Правка.** `/crm/portals/resolve` добавлен в `optionalPrefixes` в
[`portal-context.middleware.ts`](./../apps/api/src/modules/portal/crm/portals/infrastructure/middleware/portal-context.middleware.ts).
**Правило на будущее:** любой новый «публичный для SSR» эндпоинт под `/crm/` нужно сразу вносить
в этот список, иначе повторится один в один.

### 4. Все запросы CRM отвечали `400 Missing portal`

**Симптом.** Страница CRM рендерится, но каждый клиентский запрос через `$api` — 400.
При этом отдельные экраны работали.

**Причина.** Слаг портала для api-клиента хранился в модульной переменной, которую писали
**два вложенных** `PortalProvider`: внешний в `[locale]/layout.tsx` с `portalSlug={null}` и
внутренний в `[portal]/layout.tsx` со слагом. Эффекты в React выполняются снизу вверх, поэтому
внешний затирал значение внутреннего на `null`, и middleware не ставил заголовок `X-Portal-Slug`.
Работали ровно те экраны, где заголовок проставлен руками мимо общего middleware
(например `member-status-items`, формы регистрации сотрудника и участника).

**Правка.** [`crm-portal-context.ts`](./../apps/crm/modules/processes/portal/utils/crm-portal-context.ts)
больше не зависит от порядка эффектов: в браузере слаг берётся напрямую из URL через
`getRouteContext(window.location.pathname)`, а сохранённое значение осталось фолбэком
для не-браузерного окружения.

### 5. `documentation/philosophy` выведена из репозитория

Папка снята с учёта (`git rm -r --cached`) и добавлена в `.gitignore`. Из истории файлы **не удалены** —
содержимое доступно в коммите `d2731cb`; переписывать общую историю и делать force-push осознанно не стали.

Позже файлы перенесены **за пределы репозитория**, в `_private/philosophy` рядом с чекаутом, и вот почему:
игнорируемые файлы git больше не защищает. При `git checkout` другой ветки он молча перезаписывает их
отслеживаемой версией, а следующий за этим merge с удалением — стирает. Так и произошло: папка была
потеряна и восстановлена из `d2731cb`, но правки, ни разу не попадавшие в git, пропали.
**Личным документам не место внутри рабочего дерева репозитория, даже под `.gitignore`.**
